# 318. A tool named for its first use case grows siblings instead of verbs

**Part:** Part IV — Build and tooling
**Added:** 2026-09-08

## When it applies

A project accumulates small internal tools — scripts in `bin/`, make targets,
helper commands. One of them was written for a specific job and named after
that job. Later work needs a *neighbouring* job: the same data, the same
addressing, one different operation.

## The insight

**The name is the search index.** A tool called `move-block.py` does not answer
to "replace a range", "rename inside a span" or "split a theory", so the next
person — including the person who wrote it — does not find it, and writing a
30-line sibling is cheaper than the search that would have failed anyway. Each
sibling makes the next search worse, because now the concept is spread over two
names and neither is the obvious one.

The tell is a `bin/` listing with several names sharing a noun or a shape:
`move-block.py`, `replace-range.py`, `sub-range.sh`, `rename-ident.sh`. Every
one of those took a file and a line span.

**Name the tool for its domain, and make the operations verbs.** The domain
here was *blocks of a source file*; the operations were move, copy, delete,
emit, replace, sub, split, merge. Eight verbs behind one name that answers to
all eight — and one addressing grammar, so a span printed by another tool pastes
straight in.

## Evidence, and it is the uncomfortable kind

NDTHT, 2026-09-08: six scripts collapsed into `bin/block.py`, 1001 lines deleted
for 85.

The diagnosis was not new. A commit five weeks earlier had asked *"why are there
five overlapping line-range tools in `bin/`"* and answered it correctly — the
name was chosen for a May 2026 use case, so siblings were cheaper to write than
the tool was to find — and filed the consolidation as a tracked item.

**Two more siblings were then written, one of them by the agent that had read
that commit three days before.** Naming the mechanism does not disable it. What
disabled it was doing the rename.

## What to do

- **When you are about to write a script that takes the same inputs as an
  existing one, that is the signal.** Not "is there a tool for this?" but "does
  something already take a file and a span?" — the second question has an answer
  you can grep for.
- **Consolidate by adding verbs, not by adding a wrapper.** A dispatcher over
  six scripts keeps six behaviours to maintain; one tool with six code paths and
  a shared addressing layer is what removes the duplication.
- **Prove equivalence before deleting**, mechanically: run old and new on
  identical fixtures and compare bytes. That check is spent once the old tools
  are gone, so promote its durable half to a `--selftest` in the survivor rather
  than keeping the comparison script.
- **Rewrite the reach-for surfaces, not the narrative.** Instructions that name
  a dead tool (`CLAUDE.md`, skills, KB entries, memory) actively mislead;
  `history/` and spent design memos record what was run at the time and should
  stand. Getting this backwards is how a corpus becomes untrustworthy.

## The payoff that is not deduplication

Consolidating forced one addressing layer, and that is where the new capability
appeared: with a parser available, a region could be named by *entry* rather
than by line span. A documented two-step ("`query show NAME` for the span, then
the other tool to cut it") became one step, and the intermediate span — which
could go stale between the two calls — stopped existing. A KB entry changed its
prescription as a result.

Merging tools is usually presented as cleanup. The reason to do it is that the
shared layer is a place to put things.
