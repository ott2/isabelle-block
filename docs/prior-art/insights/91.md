# 91. Reserve Isabelle symbols for body text, not identifier names

**Part:** Part V — Notes, memory, discipline
**Added:** 2026-05-20

## When it applies

When choosing names for declarations (`definition`, `lemma`,
`fun`, ...) or for local Isar bindings (`have NAME:`,
`obtain ... where NAME:`) in an Isabelle theory file.

The temptation is strong to embed Isabelle symbols (`\<delta>`,
`\<Gamma>`, `\<Sigma>`, ...) in the identifier itself, because the
Isabelle/jEdit GUI renders the symbol as a single Greek glyph and
treats it as a single token.  In the editor, `wrap_\<delta>`
looks like `wrap_δ` — short, mathematical, idiomatic.

## What to do

**In identifier names, use ASCII spelt-out forms** (`wrap_delta`,
`valid_ktm_blank_in_Gamma`, `Sigma_sub_Gamma`, ...) — never the
literal `\<X>` form.

**In body text** — formula contents, type annotations,
\<comment> / text blocks, command-line antiquotations like
`@{const ...}` — keep the Isabelle symbol form; that's where it
pays for itself in PDF rendering and on-screen readability.

Survey of major reference corpora supports this split: the HOL
library uses Isabelle symbols in identifier names in only ~24
places (almost all confined to Cooper/MIR decision-procedure code,
where the Greek letters refer to specific named objects in the
formal arithmetic).  The Dalvit-Thiemann substrate AFP entry uses
this style in 6 identifiers (`fin_\<Sigma>` and similar); Balbach's
Cook_Levin in 6; the Universal_Turing_Machine entry in 0.  Outside
of small math-heavy theories, identifier-embedded Isabelle symbols
are vanishingly rare in the ecosystem.

## Why / what it avoids

The convention is a mismatch between **token tools** and **text
tools**, inherited unexamined from the upstream corpus.

Isabelle/jEdit is a *token tool*: it parses `\<delta>` as a single
symbol-token, renders it as δ, navigates it as one character,
search-finds it as one word.  Within the token-tool worldview the
shell-meta status of `<` and `>` doesn't exist — those bytes
never reach a shell.  HOL stdlib and the AFP entries that *do*
use embedded-symbol identifiers (Cooper/MIR for α-β-δ Presburger
work, Cook_Levin for σ-φ, Dalvit-Thiemann for fin_Σ, ...) were
written in this worldview and the convention costs them nothing.

A text-tool worldview pays the cost in full.  `query show
NAME`, grep, sed, ripgrep, shell pipelines, `git log -S` — all of
these see the literal six characters of `\<delta>` and treat
`<` / `>` as shell metacharacters that need single- or
double-quoting depending on call depth.  A grep invocation that
should be ten characters becomes twenty plus a multi-stage escape
mental model.  The failure mode is non-obvious:
mis-quoted-shell-argument silently matches nothing, which an agent
typically misdiagnoses as "the symbol isn't there" rather than
"the shell ate it."  Over hundreds of invocations per session
the friction compounds.

LLM-driven agents are exclusively text-tool consumers (no jEdit,
no symbol-aware completion), so they sit on the wrong side of the
affordance gap.  The convention here is therefore an
**LLM-specific style override** of an otherwise-fine
ecosystem-inherited convention: reserve Isabelle symbols for body
text (where the shell never sees them — they stay inside theory
files), and use ASCII for identifier names (which the shell sees
on every tool invocation).
