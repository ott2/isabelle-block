# 201. Doc antiquotations type-check in the global namespace

**Part:** Part 7 — Isabelle/HOL mechanisation
**Added:** 2026-07-01

## When it applies

You reference a bound variable of a proof — a `fix`ed name, a
set-comprehension binder, a schematic — inside a documentation
antiquotation (`@{term "..."}`, `@{prop "..."}`, `@{const ...}`) in a
`text` or `\<comment>` block, to make the prose track the proof. The
build then fails with a *type-unification* error (e.g. `Clash of types
"nat" and "_ set"`) pointing at the doc block, not at any tactic — even
though the identical term parses fine inside the proof.

## What to do

Do not use term/prop/const antiquotations for names that are only bound
locally. A doc antiquotation is elaborated in the theory's **global**
context: it has no access to Isar-local binders, so a local name that
collides with a library constant is resolved to *that constant* and
type-checked against its signature. In our case `sym` (a proof-local
symbol vector `nat \<Rightarrow> _`) resolved to `HOL`'s symmetric-relation
predicate `sym :: (\<alpha> \<times> \<alpha>) set \<Rightarrow> bool`, so
`@{term "sym (Suc 0)"}` clashed. Write such names as `@{text "..."}`
(verbatim, no elaboration) or as plain prose. Reserve `@{term}`/`@{const}`
for *global* names, where the type-check is a feature (it catches stale
references when a constant is renamed).

## Why / what it avoids

It avoids a build break that reads like a proof error but is a prose
error, and the harder-to-spot silent variant: a local name that collides
with a *same-typed* global constant elaborates without error but renders
the wrong symbol in the PDF. The rule of thumb — *global names get
`@{term}`, local names get `@{text}`* — keeps documentation robust
against both. Distinct from the LaTeX-rendering hazards (bare underscores
/ Isabelle symbols in comment blocks): those are pretty-printing failures;
this is a name-resolution + type-check failure at elaboration.

## The general form: the content is source, and prose is not (2026-08-29)

Two further ways `\<^term>` in a comment breaks the build, both hit in
`Diagonal_Machine`, neither a name-resolution problem:

- **A schematic variable.** `\<^term>\<open>?pos (hdr_tape ?f)\<close>`, written
  to quote a goal state verbatim, fails with *"Unbound schematic
  variable"*. Quoting a pending goal is the natural thing to want and is
  exactly what cannot be done.
- **A fragment that is not a term.** `\<^term>\<open>\<forall>p < E\<close>`,
  meaning "the `\<forall>p < E` form" — an inner syntax error at `""`,
  because the binder has no body. Prose that reads perfectly well is not
  therefore parseable.

The unifying rule is stronger than the original entry's and subsumes it:
**an antiquotation's content is source code, elaborated in the global
context, and nothing about being inside a comment relaxes that.** So the
decision is not "is this name global?" but "would this expression compile
on its own line?" — if not, a plain cartouche `\<open>...\<close>`.

Two properties make these cheap when they happen and worth knowing anyway.
The diagnostic is accurate and names the comment's line, so triage is
quick; but *a build failure whose locus is prose* is not a category one
looks for, so the minute goes on disbelieving the line number. And the
linter cannot help: `bin/lint-latex.py` checks the *shape* of what is
cited (see `[const-antiq-fact]`), not whether it elaborates, which would
need Isabelle.

**The first of those two is not reliable, corrected 2026-09-06.** A
`\<^term>` in a theory-level `text` block naming `hd` — a head map inside
the proof, `List.hd` in the global context — failed with the type clash
and **no line number at all**, in the build output and in
`isabelle build_log -H Error` alike:

```
*** Type unification failed: Clash of types "_ list" and "nat"
*** Operator:  sim_rep ta :: (nat \<Rightarrow> nat) \<Rightarrow> ...
*** Operand:   hd :: ??'a list \<Rightarrow> ??'a
```

The 2026-08-29 cases were `\<comment>` blocks inside proofs, which is
where the locus came from. So the triage move is the *operand's type*,
not the line: `??'a list \<Rightarrow> ??'a` names `List.hd` and nothing
else, and grepping the theory for the token finds the sentence. Budget
for a failure that says only what, never where — and see
[insight 93](93.md) for which single-word names invite it.

## The variant where you were not naming anything (2026-09-15)

Every case above is a *reference* that resolved wrongly. There is a third
trigger, and it is the one that reads as impossible: an antiquotation
containing **no reference at all**, only placeholder letters.

```isabelle
\<comment> \<open>... cannot contradict a \<^prop>\<open>\<not> (P \<and> Q)\<close> it has
    already normalised ...\<close>
```

`P` and `Q` here are the schoolbook letters for "some proposition", meant
as notation and not as a citation. But the enclosing lemma fixes `Q` as a
machine state, so the build stops with *Clash of types "diag\_state" and
"bool"*.

Note what this corrects: a `\<comment>` inside a proof **does** see the
proof's own fixed and free variables, so "elaborated in the global
context" is not the whole rule. The reliable rule is the weaker and
stricter one — *an antiquotation is source, and it resolves against
whatever context it sits in*, which for a proof-local comment includes
every letter the lemma fixed.

The practical consequence is a naming one, and it costs nothing to
follow: **do not write a schematic formula in prose at all.** Say "a
negated conjunction", not `\<^prop>\<open>\<not> (P \<and> Q)\<close>`. The single
capital letters that make good placeholder notation — `P`, `Q`, `A`, `E`,
`C` — are exactly the ones a machine-level lemma fixes, so the collision
is not bad luck but the common case.

**One thing the linter does catch, and it is worth more than it looks.**
`[const-antiq-forward]` fires when a `\<^const>` names something declared
*later in the same theory*. Its stated job is ordering, but because prose
antiquotations resolve in the code's namespace, it also fires the moment a
**new declaration shadows an imported one that prose already cites** — the
old sentence silently re-resolves to the new constant and becomes a forward
reference. That is how `dec_delta` was caught shadowing
`Godel_Enumeration`'s (2026-08-29); nothing else in the toolchain would have
said anything, because shadowing is legal. So `make lint-latex` is a partial
shadowing detector, with coverage exactly equal to which names the prose
happens to mention. See [insight 236](236.md).
