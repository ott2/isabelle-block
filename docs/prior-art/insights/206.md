# 206. Importing a theory does not import its session-siblings

**Part:** Isabelle session architecture
**Added:** 2026-07-03

## When it applies

You relocate a small utility theory `U` down into an ancestor session `S`
(a substrate / base session) because it is foundational and imports only `S`'s
root theory. A downstream theory `D` in a descendant session already imports
some *other* theory `B` of `S` (`imports "S.B"`), and used `U` back when `U`
lived in `D`'s own session. You expect `D` to keep seeing `U` "for free" now
that both `U` and `B` live in the same ancestor session `S`.

It does not. `D` sees only the theories it names in `imports`, plus their
transitive ancestors. `U` and `B` being siblings in `S` makes `U` neither an
ancestor of `B` nor of `D`. A *session* is a build unit and a namespace scope;
it is **not** an import — putting two theories in one session wires no edge
between them, nor from a descendant to all of them.

## What to do

Add the sibling explicitly and session-qualified: `imports "S.B" "S.U"`. The
qualification is by session name, not directory. Before relying on transitive
visibility, ask the concrete question "is `U` an *ancestor* of something `D`
already imports?" — sibling-in-the-same-session is not ancestor-of. When in
doubt the build is the oracle: an unqualified or missing import fails with
`Bad theory import` / `Undefined …`, naming exactly what to add.

## Why / what it avoids

It avoids the false economy of "drop the import, the ancestor session now
supplies it" — a plausible-sounding shortcut that does not compile, and worse,
reads as correct in a design note until the build contradicts it (this insight
was written because a handoff note asserted exactly that shortcut). Session
membership governs *building and naming*; `imports` governs *visibility*. Keep
the two mental models separate.

## The converse error: inferring unreachable from not-in-scope

*(Added 2026-08-26.)* The same two models get confused in the other direction,
and that direction is **worse, because the build does not contradict it.**

You need lemma `L`, which exists in session `A`. Your theory does not see it.
You conclude `A` is unreachable and write your own copy. But "not in scope"
only means no `imports` line names it — it says nothing about whether one
*could*. If `A` is an ancestor session, adding the import is the whole fix, and
it costs nothing at build time: an ancestor arrives as a heap image, so the
build log shows `A` in the session graph but never *Running*.

Two things let this survive review. A second lemma of the same name
**shadows** the first rather than clashing, so there is no diagnostic and no
warning — the copy compiles cleanly and looks correct. And the reasoning is
usually recorded as a confident comment ("`A` is a sibling of our ancestor, so
it is not in scope"), which was true when written and silently stops being
true the moment the session graph changes underneath it. In NDTHT the graph
changed when a join session was inserted to make two sibling reductions
reachable from one heap; a comment written after that change still asserted the
pre-change topology.

**What to do:** before writing any lemma that feels generic, `query find` the
name — it searches every session at once and does not care what is imported.
A hit in a non-ancestor session is a real constraint; a hit in an ancestor is
an import line. And re-derive session reachability from the `ROOT` files at the
time of writing rather than from a comment asserting it, especially in a tree
where the graph is still being edited.

## The third face: a theory the ROOT names that nothing imports

*(Added 2026-09-07.)* The same two models produce a third failure, and it is
the quietest of the three: **the build is green and the work is inert.**

You add lemmas to theory `X`. `X` is listed in the session's `ROOT`, so every
build elaborates it and reports OK. But no theory `imports X`, so nothing
downstream — in particular not the theory stating the session's headline
obligations — can use a line of it. `ROOT` membership got the theory *built*;
only an `imports` edge gets it *read*, and nothing in the toolchain
distinguishes those for you. In NDTHT this hid a whole session's worth of
Case 1 simulation work: the tip imported one of two siblings and the sweeps
were in the other.

Neither earlier direction catches it. Direction 1 fails to compile. Direction
2 at least makes you *want* a name you cannot see. Here you never reach for
anything, because you are writing into `X` rather than out of it, and `X`
compiles perfectly.

**What to do:** `query uses THY` (who imports it) on any theory whose contents
are supposed to reach a headline — at the moment you start adding to it, not
at the end. The complement of `query deps`, and the one people never run,
because the question "who reads this?" only occurs to you once you already
suspect the answer is nobody. A leaf is fine when it is *meant* to be one
(`Coverage` here is deliberate); it is a defect when the leaf holds a lemma
some theorem is waiting for.

**And when you do wire it up, prefer joining at the tip to stacking.** Two
expensive siblings that do not need each other should meet in the cheap theory
above both, not become a chain — the chain serialises what the scheduler was
building in parallel, and a session's build is its slowest path.
