# 289. An Isar command word cannot be a case name or a fact label

**Part:** Part — Isar syntax
**Added:** 2026-08-25

## When it applies

You name a `consider` alternative, an `obtain` case, or a `have` after
something that reads like an ordinary English word — `back`, `write`,
`then`, `next`, `also`, `finally`, `note`, `let`, `fix`, `case`,
`moreover`, `ultimately`, `done`, `apply`, `defer`, `prefer`,
`unfolding`, `using`.
A few of these are obvious; **`back` and `write` are not** — `back` is
Isabelle's backtracking proof command and `write` adjusts notation, and
they are exactly the words you reach for when naming a rewind phase, a
return leg, a reverse direction, or the arm of a machine that writes.
Both were hit in one session (2026-08-27), in a theory whose transition
families are literally called read, write and rewind: the collision rate
is highest precisely where the vocabulary is most natural.

The symptom does not name the offending word, and does not point at it:

```
Outer syntax error (line 682): proposition expected,
but keyword ( was found
At command "<malformed>" (line 671 of ...)
```

Line 671 is where the enclosing command *started*; line 682 is where the
parser gave up, which is the alternative **after** the bad one — the
parser consumed `| (back)` as the end of the previous alternative plus a
`back` command, and then met `)`. Used as a fact label the same collision
reads instead as an unterminated command: `proposition expected, but
end-of-input was found`, reported at the last line of the file.

## What to do

**This is now checked mechanically.** `bin/lint-isar-names.py` runs inside
`make lint-latex`'s recipe, so every `build-*` gates on it and the
collision is reported — with the word named and the line right — before
the build starts. That is the actual fix for a hazard like this one: a KB
entry cannot help, because nobody consults the KB before choosing a
label. Written 2026-08-27, after the entry it documents failed to prevent
two more instances in a single session.

Rename it. `back` → `rewind`, `stop` → `home`, `next` → `advance`.

Do **not** reach for a mechanical identifier renamer to do it: these are
ordinary English words, so a literal substring rename rewrites the
surrounding `text` and `\<comment>` prose too ("a machine that is merely
allowed to home early signals nothing when it homes"). That is
[insight-148](148.md)'s family — a blind renamer cannot tell a code token
from an English word any more than it can tell a stale reference from a
deliberate historical one. Edit the handful of sites directly, or
`rg -n '\bOLD\b'` afterwards and repair the prose.

**The renamer reports success either way.** A literal substring rename of
`back` to `invert` on a single file (then `bin/rename-ident.sh`, now
`bin/block.py sub`) printed a `PASS:` line naming one file and had, in the
same pass, turned "reading a run back the other
way" into "reading a run invert the other way" and three more like it.
Nothing downstream catches this: the build is green because the prose is
inside `text` and `\<comment>`, and `make lint-latex` checks rendering
hazards, not English. If the renamer is used anyway, `grep -n NEW FILE`
immediately afterwards and read every hit — the code sites are the ones
you wrote, and everything else is damage.

## Why / what it avoids

The diagnostic points at the *following* construct, so the natural
reaction is to study a line that is correct — the two builds this cost
went into re-reading a `consider` alternative that had nothing wrong with
it, and then into diffing it against the alternative before it, which
also had nothing wrong with it. Knowing that Isar keywords are live in
case-name and fact-label position turns a puzzling parse error into a
one-token fix.

The grammar command `nonterminal` is another plausible label. Its collision
in a source dead-end proof produced the same end-of-input diagnostic;
`source_nonterminal` is safe. The linter's keyword set and collision probe
now include it.

The general signal: **an outer syntax error whose reported line contains
nothing questionable is a signal to look one construct earlier**, and to
suspect that a name you chose is a command. `query at THY:LINE` names the
enclosing entry, which is the right first move, but it will confirm the
locus rather than explain it.

**The tool for a word-shaped rename (2026-10-03).** `bin/rename-thy-names.py MAP FILE...`
takes an explicit `OLD NEW` table of whole identifiers.  It renames them everywhere in
source but, in `text` / comment prose, only inside nested cartouches and `@{...}`
antiquotations, where a word is a reference.  In `.md` files it renames only inside
backticks.  Used for the MAT renames (`restate` → `ktc_set_state`, 1121 sites): the
English "restate"/"unary" in prose survived, and no build or lint could have told
otherwise.

**A code span is not proof of a reference (2026-10-05).**  The `dir` → `move`
rename trusted backticks and still did damage: `` `t/<dir>/` `` (a directory
placeholder), `` `build-<dir>` `` and `` `pcommit_read/write/dir` `` (a fragment of
`pcommit_dir`) all became `move`.  And Markdown that *describes another
development* — `related.md` and `substrate-fork.md` on Dalvit and Thiemann's
entry — must keep that development's names however they are quoted.  So a
word-shaped entry gets its own pass with every hit reviewed, and documents about
the source are excluded by file, not by syntax.  The non-word names (`mttm`,
`mt_config`) are references wherever they appear, which is what
`--md-prose` exploits.
