# 37. Unused code as a forest of rooted subtrees

**Part:** Part V — Notes, memory, discipline
**Migrated:** 2026-05-07 (from monolithic `insights.md`)

**When**: You have a codebase with many lemmas/functions and want to
identify dead code for cleanup, but naive "zero callers" lists are
misleading because (a) your main theorem is itself uncalled, and
(b) removing one unused entry cascades to reveal more.

**What to do**: Model the call graph as a DAG.  Compute three views:
1. **Roots** — entries with zero callers (direct unused).
2. **Cascade** — fixed-point: entry is unused if all its callers are
   unused.  This is garbage collection.
3. **Forest summary** — for each root, compute its *exclusive* subtree
   (entries reachable only from that root, shared with no other root).
   Sort by exclusive line count descending.

The forest summary is the actionable view: roots with large exclusive
subtrees are entire parallel proof trees that can be removed in one
sweep.  Roots with zero exclusive entries are small leaves whose
dependencies are all shared — removing them saves only the root itself.

**Why**: Naive dead-code lists conflate main theorems (intentionally
uncalled endpoints) with superseded code (accidentally unused).  The
forest summary separates them: intentional endpoints have large total
cones but modest exclusive subtrees (shared with other roots), while
superseded code has exclusive subtrees that cascade deeply.

**Anti-pattern**: chasing cascading dead entries one-by-one, where each
removal reveals the next layer.  The forest summary shows the full
picture upfront.

**When the tree already carries dead code** (added 2026-09-24): the cascade
cannot tell what *your* change orphaned from what was already dead, and if a
long dead chain hangs under code you just replaced, it can also mark live
lemmas unreachable (NDTHT: a pinned Case 1 chain with no caller made
`query unused -r` flag 76 `t/nth` entries, including two written that
hour for live callers).  Compute the *non-recursive* zero-caller list on the
pre-change commit (a scratch `git worktree`, `query -R`), then prune in
rounds: each round deletes exactly the names that are zero-caller now and
were not at the baseline, and the next round finds what that orphaned.  The
decrement's retirement took eight rounds and removed 1,900 lines, and none
of the rounds touched the pre-existing dead chain, which is a separate
decision.  `bin/prune-entries.py` does the deleting.

**Three things a zero-caller list cannot see** (added 2026-09-24, from the
first sweep after construction finished; the guards are in
`bin/unused_lib.py`, used by `bin/prune-rounds.py` and
`bin/classify-unused.py`).  A caller graph built from proof-body references
says nothing about (i) **definitions used only in statements**: they turn
zero-caller once the lemmas that unfold them go, and deleting one broke 48
proofs at once; (ii) **rules used implicitly**: `[simp]` / `[intro]` on the
header, or joined later through `declare` / `lemmas`.  Read the header line
itself, because an entry's span starts at its preamble text, and a check of
the span's first line missed every one; (iii) **entries the prose explains**:
a lemma named in a `text` block or a design doc is part of the explained
design, and deleting it leaves the explanation pointing at nothing.  The
first two break the build; the third does not, which makes it the one to
guard by tool.  With all three guarded, the NDTHT sweep kept 9 of 47
candidate roots and removed 40 entries (316 lines) cleanly.
The third guard is a default, not a verdict: when the entries it protects are
deleted *by decision*, the prose has to be repaired by hand instead, one
rewording per citation.  `--force-roots` lifts the guard for the named roots
only, so their orphans stay guarded and come back for review.  The second
NDTHT pass deleted 36 entries that way, and the repair touched eleven
theories and five documents; that cost is the reason the guard is the default.
